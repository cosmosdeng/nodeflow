# WORKFLOW.md — 标准工作流(Standard Operating Procedure)

> 本文档总结 NodeFlow 项目固定的推进节奏与标准动作列表。每个工作阶段都按下述流程执行,并在阶段关键节点提醒用户确认。

## 标准动作列表

每个阶段按固定顺序执行以下 7 步:

### 1. 整理需求列表

开始一个阶段前,先用 **todo 清单**明确本阶段要完成的功能 / 需求,作为推进依据。需求来源包括:用户直接提出、之前 TODO 规划(P 系列)、实现中发现的新需求。

### 2. 逐项实现

按需求列表顺序逐个实现功能,每实现一项更新 todo 状态(in_progress / completed)。

### 3. 过程中微调 / 新增需求

实现过程中若用户反馈问题或提出新需求,先补充进需求列表,再继续实现。允许阶段内动态调整。

### 4. 实现完后检查

功能实现后统一校验:

- **类型检查**:`npx tsc --noEmit -p tsconfig.json`
- **Lint**:`read_lints`(检查是否有新增错误)
- **单元测试**:`bun run test`(vitest 全量)
- **预览验证**:通过 preview 让用户实际操作验证功能是否符合预期

### 5. 更新所有文档

把本阶段(以及之前阶段提出但尚未记录的)**所有需求**更新到相关文档,确保文档与代码一致:

| 文档 | 更新内容 |
| --- | --- |
| `README.md` | 功能特性 / 使用说明 / 交互描述 |
| `docs/DEVELOPMENT_LOG.md` | 按时间倒序追加开发日志(功能 / 修复 / 里程碑) |
| `docs/TODO.md` | 更新 P 系列:已完成项标 `[x]` 并补充说明,待办项保持 |
| `docs/UI_UX_DESIGN.md` | 涉及 UI/UX 时:更新组件 / 交互规范、历次调整决策 |
| `docs/AI_CONTEXT.md` | 核心概念 / 数据模型 / 交互约定 / 已知问题 |
| `docs/ARCHITECTURE.md` | 架构、模块职责、数据流变化 |

### 6. 同步到 GitHub

文档与代码就绪后:

```bash
git add -A
git commit -m "<规范化的提交信息>"
git push origin main
git status -sb   # 确认工作区干净、与 origin/main 同步
```

### 7. 阶段收尾提醒

每完成一个阶段,主动向用户**汇报结果并提醒确认**,确认后再进入下一阶段。绝不擅自开始下一阶段。

## 关键约定

- **涉及 UI/UX 的改动**,先读 `docs/UI_UX_DESIGN.md` 再实施,改后保持文档与代码一致。
- **文档是代码的一部分**:任何功能变更都必须同步文档,不允许只改代码不更新文档。
- **每个阶段的全部需求**(含过程中新增)都要完整记录进文档,便于将来查询。
- **git 提交**:仅在用户确认阶段完成或用户明确要求时提交 / 推送;阶段中途避免频繁提交。
